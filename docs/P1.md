# P1: types

## Goal

Answer the linearity question while it is cheap: can affine/linear tiles
express the kernels inference needs without fighting the author? The roadmap
moves this forward from the design doc's M0 because hand-typing kernels on
paper always looks fine. A checker and an interpreter running a real
flash-attention decode loop are what answer it.

## Exit test

Flash-attention **decode** inner loop — K reuse across query blocks,
double-buffered — type-checks and matches PyTorch in the interpreter. Its
Hopper schedule type-checks too.

## The test case

32 query heads sharing one KV head (MQA decode), head dim 128, 512 KV
positions, f16 storage, f32 accumulation. The KV loop is outermost and the
query-block loop innermost, so each K/V tile is fetched once and read by every
query block — the order that stresses linearity:

```text
for each KV block, pipelined `stages` deep:
    issue copy of block i + stages-1 into the free buffer
    K, V = wait(oldest copy)
    for each query block:              # K, V borrowed by every iteration
        online-softmax update of (m, l, acc)[qb]
    K, V become the free buffers
```

The schedule — `bq`, `bk`, `stages`, where K/V are staged — is a builder
parameter. One function produces every variant; the checker decides where
each fits:

| Schedule | Threadgroup peak | apple-m-series (32 KiB) | nvidia-hopper (227 KiB) | amd-cdna3 (64 KiB) |
| --- | --- | --- | --- | --- |
| bq 8, bk 32, 2 stages | 32 768 B | ok, warns: no async copy | ok | ok, warns |
| bq 16, bk 128, 3 stages | 196 608 B | **rejected**: budget | ok | **rejected**: budget |

Interpreter against the f64 reference: max relative error 1.0e-5 (Metal
schedule) and 1.8e-5 (Hopper schedule). The f64 reference agrees with PyTorch's
`scaled_dot_product_attention` to under 1e-6, and both interpreter runs are
also checked directly against the PyTorch output at 1e-4.

## Findings

**K reuse needed no `dup`.** Zero dups in every schedule. A loop body may
borrow anything in scope and may only consume what it defines or is carried —
Rust's closure-capture rule, lexically scoped. That rule alone made "K read by
every query block" ordinary code. The design doc's fallback (explicit `dup`
plus borrow views) turned out to need only the second half.

**Per-query-block state needed a new region form.** The accumulators
`(m, l, acc)` for each query block must survive across outer iterations. An
indexed `take(arr, qb)` / `put(arr, qb, x)` needs a proof that slots are
disjoint, which a simple checker cannot give. `map_each` — move element *i* in,
yield its replacement — makes it structurally obvious. Cost: the state is three
parallel arrays, because there are no tuples of tiles yet.

**Double buffering is a typed loop carry.** The carry is `stages-1` futures
plus one free buffer, and it must have the same type every iteration. The
classic pipelining bug — prefetching into the buffer still being read — is a
use-after-move, because issuing a copy moves its destination. Prefetching past
the end of the sequence is a bounds error, caught from the loop range.

**Futures pin memory.** An in-flight copy holds its destination buffer, so the
budget counts futures. The Metal schedule fills exactly 32 KiB; one more stage
or a wider block is a compile error, not a pipeline-creation failure.

**Where it was awkward, it was not linearity.** Two things cost effort, and
both are structure: the prologue/epilogue has to be peeled (the IR has no
`Option<Future>`, so the last `stages-1` iterations are emitted separately),
and the loop carries seven values. Both were written by a Rust builder
function, which is precisely the "double-buffering is a compiler transform"
the design doc wants — here it is the transform's *output* that is checked, and
that looks like the right split: the schedule generates typed IR, the checker
verifies it.

**Verdict so far:** linear tiles do not make flash-attention decode awkward.
The design-doc risk "linearity makes common kernels awkward" is not realised
for this kernel. It is not retired: the harder case is below.

## Not answered yet

- **Warp specialisation.** The Hopper schedule type-checks for *budget*, but
  its real shape — one producer warp issuing TMA, consumer warpgroups waiting
  on 3-stage mbarriers — is not expressible. A `Future` here is waited on by
  the whole threadgroup, once. Barriers with arrival counts, and futures with
  more than one consumer, are the next piece, and the one most likely to force
  a type-system revision. This is the remaining half of the exit test.
- **GEMM A-fragment reuse across the N loop**, and the **persistent-megakernel
  arena** reused across phases with different types — the other two stress
  cases the roadmap names.
- **Layouts.** Every tile is row-major; there is nothing to check a swizzle or
  an MMA fragment against yet.
- **Uninitialised reads** of an `alloc` are caught by the interpreter, not the
  checker (a typestate question).
- **Register pressure** is not budgeted. Staging all 512 K/V rows in registers
  type-checks; it would not run well.
