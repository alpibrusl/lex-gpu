# P2: Metal, correct

## Goal

Llama-3-8B in int4 producing correct tokens on the Mac, at any speed: the full
op set in MSL, int4 dequantisation, paged KV, safetensors loading, sampling.
No fusion, no tuning; those are P3.

## Status

**First slice: typed kernels run on the GPU.** `tile_msl::program::lower`
lowers a checked `tile-front` program to one MSL kernel.
`Gpu::build_lowered` compiles it, and flash-attention decode runs on the M4
Max, matching PyTorch.

## How the lowering works

It is the simplest scheme that is right for every program the checker
accepts:

- **One threadgroup per grid instance**, with `T` threads.
- **Register tiles are distributed cyclically.** Thread `t` owns flat elements
  `t, t+T, …`. Elementwise ops between equal-sized tiles never leave the
  thread.
- **Operands another thread owns** (a matmul input, a row-broadcast vector,
  a row reduction's input) are **staged** through threadgroup scratch.
- **Threadgroup tiles** get a fixed arena offset per allocation site. They
  move through copies, waits and loop carries as *pointers*, so a rotated
  double buffer is a pointer swap.
- **`copy_async` becomes a cooperative copy at issue, and `wait` a barrier.**
  Metal has no copy engine. This is sound only because linearity proves
  nobody still owns the destination.
- **Barriers are conservative:** one before every threadgroup write, and one
  between staging and use.

## Results

Flash decode on the GPU matches PyTorch SDPA within 1e-4. It also matches the
interpreter with 5 heads on the grid; only `exp` differs, in the last bits.

The speed is the baseline, not the claim. Llama-3-8B decode shape (8 KV heads
× 4 query heads, head dim 128, f16), measured on an M4 Max:

| batch × seq | tile GB/s | % of copy | PyTorch SDPA, same layout | tile / torch |
| --- | --- | --- | --- | --- |
| 4 × 4096 | 23.4 | 5% | 379.5 | 0.06× |
| 16 × 8192 | 90.3 | 19% | 435.0 | 0.21× |

The kernel launches one threadgroup per (sequence, KV head), so batch 4 has 32
threadgroups on a 40-core GPU. Each one streams its whole K/V sequence
serially, behind 34 barrier sites and scalar dot products. P3's work is visible
in that sentence:
- split the sequence across threadgroups (flash-decoding);
- use simdgroup reductions and matrices instead of scratch staging;
- derive the barrier set from the effect graph.

(PyTorch's `enable_gqa=True` path on the 32-head layout reaches only
12.5 GB/s, which would make tile look 1.9× faster. That comparison is
misleading, so the script labels it and never uses it as the headline.)

## Findings

**The rotated double buffer broke the first lowering.** After `wait`, K
*aliases* its carry's buffer, so the loop's yields are a permutation of the
carries' storage. Assigning them one at a time read a pointer it had just
overwritten. Every head computed garbage, and no type error could see it: the
program was right; the lowering of its SSA was not. Carries are now assigned
in parallel through temporaries, and a register permutation is refused rather
than miscompiled.

**The checker's budget is not the backend's budget.** The Metal schedule that
fills 32 KiB exactly type-checks, but the lowering needs staging scratch on
top, so it doesn't fit. The backend reports "N B of tiles + M B of scratch"
instead of failing at pipeline creation. The checker cannot know M yet. Once
layouts are in the type, staging becomes explicit and the budget becomes one
number again.

**Fast math and online softmax do not mix.** The running max starts at
`-inf`, and Metal's default fast math may assume infinities away. Typed
kernels compile with fast math off. P0's kernels keep it on, so their numbers
don't move.
