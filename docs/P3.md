# P3: Metal, fast

## Goal

At least 70% of llama.cpp's Metal throughput for decode *and* prefill, with
the schedule language doing the work: simdgroup atoms, threadgroup
pipelining, graph fusion. The reference point is Ollama (llama.cpp) running
the same GGUF file on the same M4 Max.

## Status

**First slice: 4.1× (8B) and 12× (1B) faster decode, with the same
answers.** Every step was measured before it was taken.

| Model | P2 baseline | Now | Ollama | Now as a share of Ollama |
| --- | --- | --- | --- | --- |
| `llama3.1:8b` (Q4_K_M) | 6.8 tok/s | **~28 tok/s** | ~86 tok/s | 33% |
| `llama3.2:1b` (Q8_0) | 13 tok/s | **~159 tok/s** | ~275 tok/s | 58% |

Correctness did not move. On both models, all 96/96 tokens are identical to
Ollama, and top-5 log-probabilities stay within 0.007 of the f32 reference.
Decode only; prefill still runs one token at a time.

```sh
cargo run --release -p tile-rt --example profile -- --model llama3.1:8b   # where the time goes
python3 scripts/tile_vs_ollama.py --model llama3.1:8b                   # speed and correctness vs Ollama
```

## What was done, in the order the profile asked for it

**1. Measure.** `examples/profile.rs` times every call site. The P2 profile
of the 8B was:
- about 130 µs of submit-and-wait on *every* one of 418 dispatches per token.
  A 4096-element RMSNorm took 165 µs.
- matvecs at 80–100 GB/s;
- 17 ms per new sequence length, recompiling attention.

**2. One command buffer per token (8B 6.8 → 12.1, 1B 13 → 46 tok/s).**
Two things forced a CPU round trip mid-token: the KV-cache append (it
depends on the position) and attention (compiled per length). Both now take
**runtime scalars**:
- `Builder::dyn_index(name, max)` reads a value from a small scalar buffer.
  Its bound is declared, so the checker still proves every access in bounds.
- `for_range_dyn` stops at a runtime end.
- `mask_cols` masks the partial last block.

Attention is then one pipeline for every length, and the KV append is a
kernel. `Gpu::run_all` encodes a whole token into one serial compute
encoder.

**3. Split-K reductions (8B 12.1 → 22.3 tok/s).** A matvec's output tile
had 8 elements, and the lowering gave each to one thread. So 8 of 256
threads did 256-long dot products while the rest idled. Now, when a matmul
has fewer outputs than threads, each output gets a group of lanes inside a
simdgroup, the reduction is split across them, and `simd_shuffle_down`
combines the partial sums. It's a lowering rule, not a hand-written kernel.

**4. Lazy loads: fusion in the lowering (8B → 24.2 tok/s).** A register
load from a read-only parameter now becomes an address expression, not a
copy. `convert` and `dequant` over lazy operands stay lazy. A matvec's
reduction therefore reads each quantised weight straight from device
memory and dequantises it inline, with no staging and no materialised
weight tile. Anything that needs storage (loop carries, arrays)
materialises.

**5. Packed 4-bit weights and whole-row matvecs (→ 26.5 tok/s).** Q4_K
values are kept two per byte, which cuts the 8B's weight traffic from 9.4 to
6.4 GB per token. Which columns share a byte is chosen for the schedule:
column `k` with `k + kc/2`. So each nibble half is contiguous and unpacks in
the thread that owns its byte. With lazy operands the chunk can be the whole
row, so each output reduces exactly once.

## Findings

**Packing alone made it slower.** The first packed layout (`2k`, `2k+1` per
byte) cut bytes by a third and *lost* 28% of throughput: 21.9 → 15.8 tok/s.
Unpacking crossed thread boundaries, which forced a threadgroup round trip
and two extra barriers per chunk. The fix was to choose the packing to suit
the thread mapping, not the file format. This is the design doc's
layout/schedule coupling showing up in practice. The loader now records the
pairing width it packed for (`Split::pack`), and the matvec must use it.

**An optimisation deleted a barrier someone else relied on.** Lazy operands
removed operand staging, and with it the barrier at the start of each
staging step. The split-K reduction's writes to scratch had been protected,
by accident, by the *next* op's staging barrier. Without it, chunk *c+1* could
overwrite a partial sum that chunk *c*'s owner had not read yet.

The symptoms were a timing-dependent wrong answer: a different token on the
8B, and log-prob drift on the 1B that changed with batching. Every
single-kernel test passed. The model-level golden caught it. `TILE_NO_LAZY`
and `TILE_SYNC` bisected it to lazy + batched in about ten minutes.

This is the case for the design's effect-typed barriers. A barrier that
exists by convention can be removed by an unrelated change; one derived from
the effect graph cannot. Until then, the barrier is explicit
(write-after-read before a scratch write that nothing staged).

**Per-kernel GPU tests at real sizes.** `tile-metal/tests/llama_kernels_gpu.rs`
runs every Llama kernel on the GPU against the interpreter:
- every weight layout, at Llama-3-8B's hidden size;
- dynamic attention at five lengths;
- the KV append in both dtypes.

It compares absolute error against the output's scale. Per-element relative
error flagged a correct reduction, because summing in a different order
legitimately differs in the last bits on an output that cancels to near
zero.

## Where the remaining 3× is

At ~28 tok/s the 8B reads 6.4 GB per token at about 170 GB/s effective.
llama.cpp reads 4.6 GB per token at about 400 GB/s. In expected order of
payoff:

- **Vectorised loads.** Each lane loads one byte of weights, plus its scale
  and min, per value. llama.cpp's kernels load 16 bytes at a time and
  dequantise a block per thread. This needs a schedule that gives each lane
  a run of consecutive values, not a stride-32 walk.
- **Native scale layout.** Q4_K stores 6-bit scales per 32 values and one f16
  per 256. The repacked f32 scale + min per 32 is another 0.25 bytes per
  value. Reading the native block (0.5625 B/value total) would reach
  llama.cpp's byte count.
- **Fewer small dispatches.** 482 per token. RMSNorm, RoPE, KV append and
  SiLU·mul are tiny, and each is a launch. Graph-level fusion (norm into the
  next matvec's prologue, SiLU·mul into down's) is the P3 deliverable the
  design calls *graph fusion*.
- **Attention.** One threadgroup per KV head, streaming K/V serially. That's
  fine at short contexts but falls behind at long ones: this needs
  split-sequence attention (flash-decoding).
- **Prefill** runs token by token; it needs a batched path (matmul, not
  matvec), which is where `simdgroup_matrix` finally earns its place.

## Debug switches

- `TILE_SYNC=1`: dispatch one kernel at a time with a wait, and time each
  call site (`Runner::sync`).
- `TILE_NO_LAZY=1`: lower register loads eagerly, as P2 did.

Both exist because they found the race above. Keep them.
