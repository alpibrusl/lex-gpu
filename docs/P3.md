# P3: Metal, fast

## Goal

At least 70% of llama.cpp's Metal throughput for decode *and* prefill, with
the schedule language doing the work: simdgroup atoms, threadgroup
pipelining, graph fusion. The reference point is Ollama (llama.cpp) running
the same GGUF file on the same M4 Max.

## Status

**Decode meets the 70%-of-Ollama target on both models at every context
measured (0 to 1,440 positions), with the same answers.** That's 9× and 16×
faster than where P2 ended. Split-KV attention (below) made decode flat with
context; before it, the 8B fell to 20 tok/s at 1,440 positions. Prefill has
a correct batched path, but it's slow. Every step was measured before it
was taken.

| Model | P2 end | Slice 1 | Slice 2 | Slice 3 (now) | Ollama | Now as a share of Ollama |
| --- | --- | --- | --- | --- | --- | --- |
| `llama3.1:8b` (Q4_K_M) | 6.8 tok/s | ~28 | ~45 | **~60–64 tok/s** | ~88 tok/s | **68–72%** |
| `llama3.2:1b` (Q8_0) | 13 tok/s | ~159 | ~211 | **~214–218 tok/s** | ~268 tok/s | **~81%** |

The 8B range is the steady-state profile (59 tok/s) and the live
comparison (63–64 tok/s). Ollama was re-measured in the same session. This
table is at *short contexts* (under ~40 positions); the next one covers
longer ones. The 8B now reads 4.71 GB of weights per token, against
llama.cpp's 4.62.

### Decode at context

64 decode steps after the cache holds N positions (`examples/profile.rs
--context N`):

| Context | tile 8B, serial | tile 8B, split-KV | Ollama 8B | tile 1B, serial | tile 1B, split-KV | Ollama 1B |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | ~60 tok/s | **~60 tok/s** | ~85 tok/s | ~194 tok/s | **~214 tok/s** | ~269 tok/s |
| 512 | ~37 tok/s | **~62 tok/s** | ~85 tok/s | ~134 tok/s | **~227 tok/s** | ~269 tok/s |
| 1,440 | ~20 tok/s | **~58 tok/s** | ~83 tok/s | ~75 tok/s | **~218 tok/s** | ~267 tok/s |

The serial kernel runs one threadgroup per KV head and scans the whole
cache. At 1,440 positions, attention took 70% of the 8B's step (34 ms of
49). With split-KV, the 8B holds 70–73% of Ollama and the 1B 80–84% across
the range. (The 1B's serial run at context 0 was a cold first pass; its
steady state is ~214.) Ollama's figures are from the earlier session on
this machine.

### Split-KV attention (flash-decoding)

Two kernels replace the serial one for decode:
- `FlashDecode::build_split(bps)`: instance (head, split) attends over
  `bps` blocks of the cache and writes its partial state: running max `m`,
  sum `l` and unnormalised `acc`. It uses the same online-softmax `attend`
  as every other flash variant, masked at the live length.
- `FlashDecode::build_combine(bps)`: one instance per query row. It takes
  the row's global max over its splits' maxima and weights each split by
  `w = exp(m - M)`. It then sums `l = Σ w·l_s` and forms `acc` as a
  `[1, S] x [S, d]` matmul over the live splits, 8 at a time.

What the language needed:
- A second grid dimension (`grid2`/`pid2`, lowered to
  `threadgroup_position_in_grid.y`), so the split index is a checked index
  like the head.
- `Gpu::run_launches`: a launch smaller than the planned grid, so a step at
  length `len` runs only `ceil(len / (16·bps))` splits. The pipeline is
  still compiled once, for the capacity.
- Stores squeeze unit dimensions of their view, so a `[group]` state vector
  stores into a `[group, 1]` column of `part_m[row, split]`.

Partials are laid out by query row, split-minor, so a row's splits are
contiguous for the combine. The first combine looped over splits serially,
one instance per KV head. At 1,440 positions it took 83 µs per layer, more
than the attention itself. Reading llama.cpp's
`kernel_flash_attn_ext_vec_reduce` (below) led to the parallel form, which
takes 17 µs.

The runner uses the serial kernel when a step would have only one split
(under 32 positions). There, split + combine costs more: 1.17 vs 0.78 ms
per 8B token (`Attention::min_splits`). The model test's step-by-step feed
forces split attention with 16-position splits, so up to two splits are
merged on real weights. Kernel tests cover up to 16 splits against the
interpreter, and the interpreter is checked against the f64 reference.

**What we took from llama.cpp.** Ollama runs llama.cpp's Metal kernels
(`ggml/src/ggml-metal/kernels/fa.metal`, dispatched from
`ggml-metal-ops.cpp`). Its decode attention, `kernel_flash_attn_ext_vec`:
- Uses a fixed 32 workgroups per head (`nwg`), interleaved over the cache.
  It doubles the simdgroups per workgroup (up to 4) while the cache is
  longer than `2·nwg·nsg·32`. Tile instead uses contiguous splits of a
  fixed size and launches as many as the length needs. Both keep the GPU
  full at long contexts.
- Reduces with a separate kernel: one threadgroup per output row, one lane
  per workgroup, then `simd_max` and `simd_sum` across lanes. Tile's
  combine now has that shape.
- Runs each simdgroup through 32 keys per iteration, with no threadgroup
  barrier inside the loop. Tile's split kernel still pays ~12 µs per
  16-position block, mostly latency: staging through threadgroup memory,
  and reductions separated by barriers. That's why splits are only 2
  blocks deep. It's the next thing to take from llama.cpp's design.

Batched verify and prefill still use the serial causal kernel
(`build_causal`). The same split applies there.

### The batched forward pass (prefill and speculative verification)

`Runner::forward(tokens, all)` runs up to 16 tokens through the model in one
command buffer. `prefill` chunks a prompt through it, and `truncate` rolls
the KV cache back, which speculative decoding needs. New kernels:
- `matmul_q` for T rows. Each simdgroup owns several weight rows and keeps
  an accumulator per (row, token), so each weight is read once for the
  whole batch.
- `rmsnorm_rows`, `rope_rows`, `kv_append_rows`.
- `FlashDecode::build_causal`: T new queries in the natural
  `[token, head]` layout, each query block masked at its own position.
  `mask_cols` now takes an affine limit.

The golden test feeds every prompt four ways: token by token, prefill in 4s,
prefill in 16s, and batched verify returning every position's logits. All
four match the Ollama-checked reference on both models (worst 0.006).

Measured on a 512-token prompt:

| | 8B | 1B | Ollama 8B | Ollama 1B |
| --- | --- | --- | --- | --- |
| prefill, best chunk | 112 tok/s (chunk 4) | 638 tok/s (chunk 8) | ~900 tok/s | ~6,000 tok/s |
| verify 3 tokens vs 1 decode step | 1.38–1.45× | 1.28× | — | — |

Prefill is 8× short of Ollama on the 8B. The small-batch matmul runs out at
about 4 tokens, and attention scans the cache serially: prefill needs the
SIMD-group matrix path and split-KV attention.

For speculative decoding, the 1B guesses the 8B's next token 83% of the
time (`examples/accept.rs`, 192 tokens of easy text). With verify at about
1.45× a step and the 1B's 4.7 ms per draft, 2 drafted tokens project to
~1.25× over plain decode at short context. That isn't enough to beat Ollama
yet. It becomes enough once verify costs about 1.1× a step (attention and
the smaller kernels) and the draft model is faster.

Correctness did not move. On both models, all 96/96 tokens are identical to
Ollama, and top-5 log-probabilities stay within 0.007 of the f32 reference.
Weights are still dequantised bit-for-bit as ggml does it.
Decode only; prefill still runs one token at a time.

python3 scripts/tile_vs_ollama.py --model llama3.1:8b                   # speed and correctness vs Ollama

## What was done, in the order the profile asked for it

**1. Measure.** `examples/profile.rs` times every call site. The P2 profile
of the 8B was:
- about 130 µs of submit-and-wait on *every* one of 418 dispatches per token.
  A 4096-element RMSNorm took 165 µs.
- matvecs at 80–100 GB/s;
- 17 ms per new sequence length, recompiling attention.

**2. One command buffer per token (8B 6.8 → 12.1, 1B 13 → 46 tok/s).**
Two things forced a CPU round trip mid-token: the KV-cache append (it
depends on the position) and attention (compiled per length). Both now take
**runtime scalars**:
- `Builder::dyn_index(name, max)` reads a value from a small scalar buffer.
  Its bound is declared, so the checker still proves every access in bounds.
- `for_range_dyn` stops at a runtime end.
- `mask_cols` masks the partial last block.

Attention is then one pipeline for every length, and the KV append is a
kernel. `Gpu::run_all` encodes a whole token into one serial compute
encoder.

**3. Split-K reductions (8B 12.1 → 22.3 tok/s).** A matvec's output tile
had 8 elements, and the lowering gave each to one thread. So 8 of 256
threads did 256-long dot products while the rest idled. Now, when a matmul
has fewer outputs than threads, each output gets a group of lanes inside a
simdgroup, the reduction is split across them, and `simd_shuffle_down`
combines the partial sums. It's a lowering rule, not a hand-written kernel.

**4. Lazy loads: fusion in the lowering (8B → 24.2 tok/s).** A register
load from a read-only parameter now becomes an address expression, not a
copy. `convert` and `dequant` over lazy operands stay lazy. A matvec's
reduction therefore reads each quantised weight straight from device
memory and dequantises it inline, with no staging and no materialised
weight tile. Anything that needs storage (loop carries, arrays)
materialises.

**5. Packed 4-bit weights and whole-row matvecs (→ 26.5 tok/s).** Q4_K
values are kept two per byte, which cuts the 8B's weight traffic from 9.4 to
6.4 GB per token. Which columns share a byte is chosen for the schedule:
column `k` with `k + kc/2`. So each nibble half is contiguous and unpacks in
the thread that owns its byte. With lazy operands the chunk can be the whole
row, so each output reduces exactly once.

**6. Runs of consecutive values per lane (8B → 33.4 tok/s).** In a split-K
reduction, each lane now takes runs of `V` consecutive elements rather than
one element every 32, so the Metal compiler can merge a run's loads. The
best `V` measured was 4 before step 7 and 8 after it (`TILE_VEC`).

**7. Native scales, hoisted per group (8B → ~45, 1B → ~211 tok/s).**
Scales stay in the file's own form:
- Q8_0: an f16 per 32 values.
- Q4_K and Q6_K: a small integer per group times an f16 `d` per super-block.
  Two-level scales go through the same checked `dequant`
  (`scale = dequant(sc, d)`).

That brings the 8B's weight traffic down to 5.1 GB per token, against
llama.cpp's 4.6. The lowering also records a lazy dequantisation's parts:
value per element, and scale and min per group. When a reduction's run fits
inside a group, it evaluates `d·sc` and `dmin·m` once per run, not once per
weight.

**8. One pass over packed 4-bit weights (8B → ~52 tok/s).** With lazy loads
there's no reason to split each chunk into nibble halves any more: that
layout existed so each thread would own the bytes it unpacked. Q4_K goes back
to plain pairs (column `2k` low, `2k + 1` high) and a single `dequant4`
(`Nibbles::Pairs`). The reduction loads each byte once and splits it with
constant shifts.

**9. Parallel row reductions (RMSNorm 23 → 8.4 µs).** A row reduction with
fewer rows than threads now gets lanes per row, combined with shuffles within
a simdgroup and through scratch across simdgroups. Elementwise ops over lazy
operands stay lazy, so RMSNorm reads `x` directly.

**10. Q6_K as bit planes (8B → ~60 tok/s, 4.71 GB/token).** Q6_K values are
stored the way the file stores them: a 4-bit plane two per byte and a 2-bit
plane four per byte, 0.75 bytes per value. A new `dequant6` op recombines
them, and the reduction unpacks four values per step from three bytes.
Runs are 16 values per lane for packed weights and 8 otherwise; each is what
the sweep measured best.

**Profiling with GPU timestamps.** Per-dispatch wall time is dominated by the
~110 µs CPU round trip, so it can't rank kernels. The profiler now reads
each command buffer's own `GPUStartTime`/`GPUEndTime`. It also splits a
batched token into CPU encoding (0.11 ms) and GPU execution: the GPU is the
bottleneck.

## Findings

**Fewer bytes made it slower, again.** Native two-level scales cut traffic
from 6.4 to 5.1 GB per token, and throughput *fell* from 33.4 to 23.8 tok/s.
Forming `d·sc` and `dmin·m` for every weight costs four loads and two
multiplies per value, and the kernel was bound by instructions, not bytes.
Hoisting the group terms turned the same bytes into 43 tok/s. As with
packing, the byte count was necessary but not sufficient: what matters is
what each thread does per byte.


**Packing alone made it slower.** The first packed layout (`2k`, `2k+1` per
byte) cut bytes by a third and *lost* 28% of throughput: 21.9 → 15.8 tok/s.
Unpacking crossed thread boundaries, which forced a threadgroup round trip
and two extra barriers per chunk. The fix was to choose the packing to suit
the thread mapping, not the file format. This is the design doc's
layout/schedule coupling showing up in practice. The loader now records the
pairing width it packed for (`Split::pack`), and the matvec must use it.

**An optimisation deleted a barrier someone else relied on.** Lazy operands
removed operand staging, and with it the barrier at the start of each
staging step. The split-K reduction's writes to scratch had been protected,
by accident, by the *next* op's staging barrier. Without it, chunk *c+1* could
overwrite a partial sum that chunk *c*'s owner had not read yet.

The symptoms were a timing-dependent wrong answer: a different token on the
8B, and log-prob drift on the 1B that changed with batching. Every
single-kernel test passed. The model-level golden caught it. `TILE_NO_LAZY`
and `TILE_SYNC` bisected it to lazy + batched in about ten minutes.

This is the case for the design's effect-typed barriers. A barrier that
exists by convention can be removed by an unrelated change; one derived from
the effect graph cannot. Until then, the barrier is explicit
(write-after-read before a scratch write that nothing staged).

**Per-kernel GPU tests at real sizes.** `tile-metal/tests/llama_kernels_gpu.rs`
runs every Llama kernel on the GPU against the interpreter:
- every weight layout, at Llama-3-8B's hidden size;
- dynamic attention at five lengths;
- the KV append in both dtypes.

It compares absolute error against the output's scale. Per-element relative
error flagged a correct reduction, because summing in a different order
legitimately differs in the last bits on an output that cancels to near
zero.

## Where the rest is

Bytes are at parity with llama.cpp (4.71 vs 4.62 GB per token). The big
matvecs run at 380–390 GB/s, which is the bandwidth ceiling. What remains:

- **Prefill** runs token by token. This is the other half of P3's exit test
  and the bigger job: it needs a batched matmul path, which is where
  `simdgroup_matrix` finally earns its place.
- **Fewer small dispatches.** 482 per token. RMSNorm, RoPE, KV append and
  SiLU·mul are tiny, and each is a launch. Graph-level fusion (norm into the
  next matvec's prologue, SiLU·mul into down's) is the P3 deliverable the
  design calls *graph fusion*.
- **Attention's per-block latency.** Split-KV made decode flat with
  context, but a 16-position block still costs ~12 µs. llama.cpp's vec
  kernel keeps each simdgroup barrier-free over 32 keys at a time.
- **Prefill** runs token by token; it needs a batched path (matmul, not
  matvec), which is where `simdgroup_matrix` finally earns its place.

## Debug switches

- `TILE_SYNC=1`: dispatch one kernel at a time with a wait, and time each
  call site (`Runner::sync`).
- `TILE_NO_LAZY=1`: lower register loads eagerly, as P2 did.
- `TILE_VEC=n`: consecutive values per lane in split-K reductions
  (default 16 for packed weights, 8 otherwise).
- `cargo run -p tile-msl --example emit -- matvec q4k 4096 4096`: print the
  MSL a kernel lowers to.
- `TILE_BPS=n`, `TILE_MIN_SPLITS=n`: blocks per split-KV split (default 2)
  and the fewest splits worth splitting for (default 2; a large value keeps
  the serial kernel).

Both exist because they found the race above. Keep them.
