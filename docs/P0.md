# P0: the spine

## Goal

Prove the toolchain before designing the language on top of it. One kernel from
tile IR to a number on real hardware, with a test harness anyone can trust.

## Exit test

RMSNorm at **≥ 90% of the copy ceiling**, output matching the CPU reference
within tolerance. `cargo run --release -p tile-bench` prints both and exits
non-zero if either fails.

## Why a copy kernel is the denominator

Absolute GB/s means nothing without knowing what the machine can do. Apple
publishes peak bandwidth figures (roughly 400 GB/s on an M-series Max, 800 on
an Ultra) but peak is not reachable by any kernel, so scoring against it just
produces a number nobody can act on.

`copy` is the simplest kernel that does nothing but move bytes, measured
through the same harness, on the same device, at the same moment. Whatever it
reaches is the practical ceiling, and the ratio to it is the only figure that
says whether RMSNorm is leaving bandwidth on the table.

It is not a *perfect* ceiling — one vec4 per thread and a 256-thread
threadgroup are the simplest thing that issues wide enough loads to be worth
measuring, not a tuned choice. The harness therefore prints absolute GB/s as
well, so a ceiling that is itself bad is visible rather than flattering.

## Bytes accounting

Every bandwidth number uses `Kernel::ideal_bytes()`: each input read once, each
output written once. For RMSNorm over `rows × cols` that is
`2 × rows × cols + cols` elements.

This is an ideal, not a measurement. The emitted RMSNorm makes two passes over
each row — one to reduce, one to scale — so on a row that misses cache it pays
real traffic the accounting does not count, and the reported GB/s will fall
short of the ceiling for that reason alone.

That gap is the point. Closing it means staging the row in threadgroup memory
during the first pass instead of re-reading it: a 4096-column f32 row is 16 KB,
which fits inside Apple's 32 KB threadgroup budget. That is a *scheduling*
decision — same algorithm, different placement — and it is precisely the kind
of decision P3's schedule language is supposed to make, and to make
differently per target. P0 deliberately leaves it undone so there is a real
gap to close later.

## Numerics

Float paths are not bit-exact against the reference and are not expected to be:
the GPU reduces in a tree across simdgroups, the CPU reduces sequentially, and
over 4096 terms those legitimately disagree in the last bits. The tolerances
live in `tile_ir::reference` (`TOL_F32`, `TOL_F16`) and are part of the
contract, not a fudge factor discovered after the fact.

Accumulation is f32 regardless of storage type; only the store narrows. The
reference implements the same rule, so an f16 mismatch means the kernel is
wrong rather than that f16 is imprecise.

## Layering

```text
  Kernel            what to compute. No target anywhere in it.
    + Target        the hardware table. Data, not code.
    = Plan          launch geometry, memory budget, derived constants.
      -> backend    emits source from (Kernel, Plan).
```

The planner already rejects rather than silently degrading: an unaligned
column count, a threadgroup scratch allocation larger than the target's budget,
or more simdgroups than the single-stage reduction can handle are all errors at
plan time. That is the design doc's "reject a layout the target cannot load
rather than emitting a slow path silently", at the only scale P0 can express
it.

## What P0 does not do

No layout algebra, no linear types, no effects, no schedule language, no
quantisation, no fusion, no autotuning, no MLIR. The dependency list is `half`
and, on macOS only, `metal`.

## Known gaps to carry into P1

- The copy kernel is not a tuned ceiling (see above). If it measures far below
  the device's rated bandwidth, tune it before trusting the ratio.
- `Plan` hardcodes `vec_width = 4` and a 256-thread preference. Both become
  searched parameters.
- `Gpu::download` is unchecked with respect to element type; a real runtime
  hands out typed buffer handles.
- Kernels are compiled from source at run time. Shipping needs a precompiled
  metallib.
- The NVIDIA target row does not exist yet. It is a P1 deliverable and it is
  the insurance against a Metal-shaped abstraction.
